## Проверяемые гипотезы

1. Абсолютный PA=0.25TL может оставить слишком мало времени после warm-start.
   В build вызов resize_dp использовал общий dp_deadline вместо дедлайна build.
   `LOCAL_BUDGET=1` ограничивает только этот вызов; не меняет длину общего поиска.
2. Конструкторы перебирались блоками; дорогая первая группа может вытеснить остальные.
   `RANK_FAIR=1` чередует конструкторы между наборами. Изменяет также RNG-поток:
   это полный эффект перестановки, а не чистое измерение разнообразия.
3. Глубокий поиск отсекал rank>=6. round увеличивался и после старта из элиты.
   `RANK_COVER=1` использует отдельный счётчик построенных стартов, весь rank,
   распределяет размер чанка по числу наборов. Это связанный прототип покрытия
   портфеля, не изолированная абляция одной строки.
4. При A=0 одиночные переносы между непустыми офисами невозможны. При большом
   alpha полезная пара может состоять из двух по отдельности плохих изменений.
   `EXCHANGE=1/2` добавляет count-preserving обмены в существующий polish.
5. Полезность оператора на фиксированном checkpoint не равна полезности в полном
   solver: новый оператор отнимает время у ALNS, DP и конструкторов.

Все переключатели нового поиска выключены по умолчанию. `SEARCH_TRACE=1` пишет
диагностику в stderr, не создаёт файлов. `WARM_DECODE=0` — диагностическая абляция
декодера генетического старта. Основной TL=280 не изменён.

## Первичные источники и выбранные разновидности

### ILS

[Lourenço, Martin, Stützle, Iterated Local Search (2001/2003)](https://arxiv.org/abs/math/0102188),
[авторская расширенная глава Framework and Applications](https://iridia.ulb.ac.be/~stuetzle/publications/LouMarStu10.pdf).
ILS следует цепочке локально улучшенных решений; важны взаимодействие perturbation,
локального поиска и принятия, а не только сила разрушения. Для нашей задачи
`SEARCH_MODE=1` использует случайное снятие сайтов, географическое снятие, половину
зоны, обмен офиса; затем recreate, repair_sizes, обмены и polish. Сила зависит от
застоя. Улучшение принимается, после четырёх неулучшений разрешён перезапуск цепочки
из последнего допустимого результата; рекорд сохранён отдельно. Два worker дают
две цепочки, внешний портфель сохраняется. Это ILS с ограниченным по времени
локальным улучшением, а не доказанным достижением локального оптимума.

Для warm-start та же схема применяется к раннему допустимому checkpoint в отдельном
исследовательском драйвере. Важно измерить стоимость восстановления: дешёвое
разрушение может оставить слишком мало времени, чтобы восстановить навыки и A=0.

### VNS / VND

[Mladenović, Hansen, Variable neighborhood search, 1997, DOI](https://doi.org/10.1016/S0305-0548(97)00031-2),
[копия оригинальной статьи на сайте университета](https://staff.fmi.uvt.ro/~daniela.zaharie/am2016/proiecte/tehnici/VNS/originalVNS.pdf).
Метод систематически меняет окрестность; улучшение возвращает поиск к первой.
`SEARCH_MODE=2` переключает четыре описанных семейства разрушения, принимает
улучшения и сбрасывает уровень. `EXCHANGE=2` — ограниченный VND внутри пары зон:
сначала 1↔1, затем 2↔2, включая обмен с неназначенным пулом. После успешного хода
перебор начинается заново. Отдельные классы нагрузки и навыков в пуле сохраняются
через экстремумы числа задач, выгодные и случайные сайты. Перестройку границ
обеспечивает существующий resplit; работников — repair/greedy_workers и существующие
skill moves. Окрестности не вложены строго по радиусу; это эвристическая реализация.

### Tabu search

[Glover, Tabu Search—Part I, 1989](https://pubsonline.informs.org/doi/abs/10.1287/ijoc.1.3.190).
Краткосрочная память и aspiration позволяют избегать циклов, сохраняя переходы
через ухудшение. `SEARCH_MODE=3` — sampled tabu search по результатам shake+descent:
один кандидат на итерацию, хеш всего назначения, запрет повторного состояния на
семь итераций, не более 64 записей; новый рекорд преодолевает tabu. Допустимый
нетабу-кандидат принимается даже при ухудшении. Это не полный best-admissible TS
и не tabu по одному сайту: последний слишком легко блокирует полезный составной
обмен. Коллизия хеша может консервативно отвергнуть переход, но не разрешает
недопустимое решение. Память не переносится между чанками/процессами.

Для выбора офисов более дешёвый вариант — tabu по маске офисов с повторным допуском
после tenure; существующий OVNS использует постоянное множество уже посещённых
масок. Оно предотвращает повторный вход даже после изменения окружения, что может
быть нежелательно. Новый TS не подменяет OVNS без сравнений.

### Go With the Winners

[Aldous, Vazirani, “Go With the Winners” Algorithms, FOCS 1994, авторский PDF](https://people.eecs.berkeley.edu/~vazirani/pubs/winners.pdf).
Идея — переносить ресурсы от неудачных траекторий к перспективным, продолжая их с
независимой случайностью. Доказательства статьи относятся к поиску в дереве и не
дают гарантий для SZO. `SEARCH_MODE=4` — эвристическое resampling четырёх траекторий
внутри worker: равные временные шаги, после волны худшие две заменяются копиями
двух выбранных; сохраняется отличающийся набор офисов либо не менее 5% назначений.
Нет crossover; RNG продолжает двигаться, поэтому клоны получают разные perturbation.
В памяти четыре траектории и служебные снимки, O(N), без внешних библиотек. Малый бюджет
может дать лишь одну волну; число clones/iterations печатается явно. Раннее
размножение лучшего proxy до восстановления допустимости опасно потерей ниш навыков.

## Что переносится из v5

В `V5_LOG_AUDIT.json` перечислены реальные локальные строки выполнения стадий:
107 stderr v5 и 203 stderr v5.2 содержат строки MIP/region со статусом и before/after.
Это включает исторические ревизии и отдельные диагностические прогоны, не столько
независимых тестов. По отсутствию строки нельзя заключать, что библиотека отсутствовала.
Серверные причины ухудшения неизвестны; файловая система сервера не исследовалась.

Перенесена идея совместного переназначения уже занятых сайтов и компактного ремонта
баланса. В native обмене сначала снимается весь набор, затем строятся новые оболочки;
проверяются все входные точки, включая свободные сайты и закрытые офисы. Это позволяет
без MILP использовать безопасное сжатие и последующее расширение зон. Гарантируется
монотонность принятого хода по настоящей цели, но не глобальная оптимальность.

Группирование по одинаковому числу задач и навыкам даёт точную редукцию выбора
наиболее прибыльных сайтов только при фиксированных разрешённых областях,
фиксированной доступности навыков и отсутствии различий в конфликтных инцидентностях.
При альтернативных областях нужно учитывать конфликты областей и уникальность сайта;
при свободной геометрии такой группировки недостаточно. Наши пулы до 20 сайтов и
128 проверяемых положительных предложений — эвристические ограничения, не точная
редукция. Существующий DP не заменён. Он по-прежнему полезен при фиксированных
территориях; новые ходы меняют территории и состав сайтов.

Сочетание совместимых областей, path relinking и перестройка трёх зон остаются
возможными расширениями, а не реализованными улучшениями этой серии. Постоянный
элитный пул уже есть; новый GWW сравнивается с ним, а не с решателем без обмена элитой.

## Корректность и воспроизводимость

`src/test_exchange.cpp` проверяет принятые составные ходы полной verify и сравнивает
size/load/need/cntSkill/cov/incov/sig с полным пересчётом. После отказа и undo назначение,
маска офисов и журнал обязаны вернуться к исходным. Есть A=0, коллинеарность,
совпадения точек, многопрофильные работники. Это property-check, а не oracle глобального
оптимума. Исходный tools/test_geometry_state.cpp проверяется отдельно.

`run.py` фиксирует хеши входов и бинарников, NT=2, exit code, реальные wall-time,
пиковый RSS через /usr/bin/time и официальный валидатор. При timeout останавливается
вся группа процесса; валидный checkpoint не превращает RE/TLE в успешный запуск.
`post.cpp` читает фиксированный checkpoint только в локальном исследовании и никогда
не включается в ZIP. `post_bench.py` сравнивает polish, обмены, ILS/VNS/TS/GWW на одном
checkpoint при одинаковом времени; это отдельный тип доказательств от full60.

Development: generator seed 461000+100*j; holdout: 491000+100*j, классы заранее
заданы в PREREGISTRATION.json. Holdout генерируется после фиксации кода. Для tightA
явно задан A=0. Solver seeds development 301–303, holdout 401–403. Открытые входы
используются только для совместимости/регрессий. Для huge предусмотрен отдельный
TL180: TL60 может главным образом измерять качество построения старта.

Численные результаты и вердикт: `experiments/v4_local_search/REPORT.md`.

## SCIP/HiGHS: восстановление без фиксированных оболочек

По дополнительному запросу пользователя подготовлен `repair_mip.py`: оба backend
решают одну и ту же линейную модель. Среда и версии зафиксированы в REQUIREMENTS.txt;
пакеты установлены только в локальное исследовательское окружение. Эта Python-модель
не включается в серверный ZIP.

Для выбранного множества сайтов S разрешены новые назначения, отказ от обслуживания,
открытие/закрытие офисов без фиксированных сайтов и новая раздача работников.
Остальные назначения фиксированы. Для сайта допускаются три лучших дорожных офиса,
прежний офис и ближайший геометрически. Это ограниченная область поиска, а не полный
оптимум исходной задачи. Работники агрегируются по одинаковым профилям навыков:
один бинарный профиль на офис, суммарно не больше числа работников профиля. Такая
редукция точна, поскольку второй идентичный работник в одном офисе ничего не добавляет.

Модель содержит уникальность сайта, ёмкости, непустоту открытого офиса, maxDifference
по числу сайтов, min/max нагрузки по задачам и затраты на офисы. Начальное допустимое
решение передаётся через warm start. Геометрия добавляется итеративно: после целого
решения строятся реальные оболочки, проверяются **все** входные точки. При общем
покрытии точки двумя зонами сокращается поддерживающее множество выбранных сайтов;
сумма соответствующих бинарных переменных ограничивается размером множества минус 1.
Для офиса без фиксированных сайтов в поддержку включается переменная открытия.
Обоснование — монотонность выпуклой оболочки при добавлении точек. Пересечение
многоугольников без общей входной точки не порождает запрета.

Если оптимум текущей релаксации геометрически допустим, он оптимален **в выбранной
окрестности**. Иначе добавляются запреты и задача решается снова. При лимите возвращается
только проверенный incumbent; bound относится к оставшейся релаксации. В Python
геометрия использует Shapely, как официальный валидатор; это не заявление о полном
совпадении Shapely с точными binary64-предикатами C++ на всех вырожденных входах.

Проверка `oracle_repair.py`: 30 новых маленьких задач, независимый полный перебор
назначений сайтов и работников, оба backend — 60/60 совпадений. В 18 решениях
действительно добавлялись геометрические cut, максимум три. Проверялись A=0,
коллинеарность, совпадающие координаты, отсутствие работников и недоступный навык.

Результат первой окрестности: выбор 24/48 сайтов по выгоде не дал прироста на восьми
зрелых checkpoint; это содержательный отрицательный результат, а не основание
увеличить время MIP. Для huge Python-обработка геометрии/валидации вышла за бюджет:
три процесса превышают принятый порог wall, хотя вернули валидный JSON. Они отмечены
как неуспешные в repair10/results.json.

Вторая окрестность освобождает последовательные слои вершин оболочек двух соседних
зон, затем добавляет ближайшие свободные сайты. repair_peel20: все 32 процесса прошли
порог времени и валидатор. Оба backend независимо подтвердили одинаковые улучшения
alphabig и large; при бюджете 128 сайтов также cluster. Они показывают, что выбор
свободных переменных важнее самого применения более мощного solver.

В alphabig улучшение 2674.688649 достигается шестью изменениями: два сайта переходят
из офиса 5 в 3, два снимаются из 3, два свободных добавляются в 5. Количества сайтов
и нагрузки всех офисов сохраняются; это пример механизма, не правило под ID офиса.
На его основе реализован общий `balanced_cycle_descent`: цикл A→B→свободные→A
из одно- или двухсайтовых пакетов одинакового количества и суммы задач. Все снятия
выполняются до вставок; конечная геометрия/работники проверяются существующим Engine.
Пулы и число альтернатив ограничены, поэтому native поиск эвристический. Новый флаг
`BALANCED_CYCLE=1 FINAL_EXCHANGE=2` заменяет только оператор в свободном финальном
времени. Без этих флагов новый цикл не запускается.

Ссылки на официальные интерфейсы и LNS: [HiGHS Python API](https://ergo-code.github.io/HiGHS/stable/interfaces/python/example-py/),
[SCIP RENS](https://www.scipopt.org/doc-9.1.1/html/heur__rens_8h.php),
[SCIP ALNS](https://www.scipopt.org/doc-9.2.4/html/heur__alns_8c.php).
RENS фиксирует целочисленные значения LP/NLP и сужает остальные; наш прототип не
называется RENS, поскольку выбирает переменные по геометрическим слоям и incumbent.
Идеи RINS/RENS уместны лишь после появления полезной релаксации геометрии: релаксация
без неё может рекомендовать одновременно несовместимые назначения.

Дополнительный oracle с тремя офисами, повторяющимися профилями работников и
нулевыми ёмкостями: 12 новых задач × два backend, 24/24 совпадений с полным
перебором; четыре запуска добавили cut. Всего две независимые маленькие серии
дают 84 сравнения на 42 задачах. Native транзакции проверены на 24 000 случайных
изменений до шести сайтов и 80 запусках инвариантов самого цикла. Подробности,
неудачные серии, проверка ZIP и окончательный вердикт — в отчёте.

Итог полного сравнения цикла: development mean−0.3254%, независимый holdout
mean+0.0860%, median0, W/T/L8/5/11; при расширении alphabig до шести seed отношение
медиан−1.0489%. Критерий принятия не выполнен. Контроль с одного checkpoint показал
и положительный эффект alphabig, и потерю tightA при замене части прежнего boundary
на цикл. Это объясняет, почему монотонность составного хода не гарантирует улучшения
полного алгоритма. Новые defaults не включены; safe-ZIP остаётся экспериментальным.
