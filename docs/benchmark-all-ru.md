# Возобновляемый прогон всех решателей с TL280

Скрипт: `tools/benchmark_all.py`. Запускать из корня проекта. Длинные прогоны скрипт запускает только по команде `run`; `plan` только собирает каталог, `status` показывает прогресс.

## Запуск

```bash
cd .
.venv/bin/python -u tools/benchmark_all.py plan
.venv/bin/python -u tools/benchmark_all.py run
```

По умолчанию: **TL280, NT=2, seed 1,2,3**, один решатель одновременно, два разных физических ядра. Ядра выбираются автоматически. Все тесты и все найденные конфигурации включены. Первая команда фиксирует исходники, тесты и настройки; вторая собирает и запускает. Готовые сборки тоже кэшируются. Первая сборка десятков версий может занять заметное время.

**Остановить: Ctrl+C один раз.** Текущий запуск будет остановлен, предыдущие результаты останутся. Повторить ту же команду `run`: готовые запуски пропускаются; прерванный начинается заново с полным TL280. Закрытие терминала обрабатывается через SIGHUP, обычное завершение процесса — через SIGTERM. При выключении питания теряется только незавершённая работа; атомарные записи и проверки хешей защищают готовый кэш. Не использовать `kill -9` для штатной остановки. После принудительного убийства Python независимый watchdog всё равно завершит дочерний процесс к TL+3 с (плюс до секунды на kill); до этого его блокировка не позволяет перекрыть измерения новым запуском.

Ограничить одну сессию:

```bash
.venv/bin/python -u tools/benchmark_all.py run --max-runs 20
.venv/bin/python -u tools/benchmark_all.py run --hours 2
.venv/bin/python tools/benchmark_all.py status
```

`--max-runs 20` означает до 20 новых запусков, включая невалидные ответы и ошибки. `--hours 2` запрещает начинать новые сборки/запуски после двух часов; начатая сборка или задача завершается. Сборки и проверки тоже расходуют время сессии. Команда `status` работает и во время бенчмарка; сводная CSV обновляется примерно раз в минуту и при завершении сессии.

Для нового исследования с двумя одновременно работающими решателями и одним seed:

```bash
.venv/bin/python -u tools/benchmark_all.py run \
  --out results/local/all_solvers_tl280_j2_s1 --jobs 2 --seeds 1
```

Нужно четыре разных физических ядра. Можно указать пары явно: `--jobs 2 --cpus '18,19;20,21'`. Скрипт проверяет доступность и отсутствие SMT-соседей среди выбранных ядер. Одинаковая пара «тест × seed» всегда закреплена за одними CPU для всех вариантов. Порядок блоков и вариантов перемешан воспроизводимо. Занятые другим таким бенчмарком CPU защищены файловыми блокировками; посторонняя нагрузка компьютера автоматически не устраняется.

Настройки TL, seeds, число параллельных задач и CPU фиксируются при создании исследования. Для их изменения, новой версии скрипта/компилятора/среды, обновлённых исходников или новых тестов использовать **другой `--out`**. Старый каталог продолжает проверять замороженные версии. Результаты разных TL автоматически не смешиваются.

## Размер полной матрицы

На текущем снимке найдены **64 уникальных исходника, 81 конфигурация и 657 уникальных тестов**. С тремя seed это **159651 запуск**. Если каждый использует все 280 секунд, бюджет одного слота — **12417,3 часа / 517,4 суток**; двух слотов — около 258,7 суток, плюс сборки и валидация. Маленькие задачи могут заканчиваться раньше. Это объём полной матрицы, а не обещание, что она практически необходима целиком.

Можно начать с нужной части, затем расширять охват **в том же каталоге**, сохраняя кэш:

```bash
# Четыре основные версии на пяти опубликованных тестах.
.venv/bin/python -u tools/benchmark_all.py run \
  --solver experiments/server_v4/artifacts/package/main.cpp \
  --solver experiments/server_v8/artifacts/package/main.cpp \
  --solver experiments/v8_exact_neighborhoods/artifacts/final/main.cpp \
  --solver solver/solve.cpp \
  --case task/instance --max-runs 20

# Потом продолжить всю матрицу.
.venv/bin/python -u tools/benchmark_all.py run
```

Фильтры `--solver` и `--case` — подстроки имён/ID, повторённые фильтры объединяются по «или». Пустой фильтр означает все. `solver/solve.cpp` встречается также в путях старых модульных снимков, поэтому для выбора только текущего решателя взять его точный ID из `catalog_variants.csv`. `plan` с фильтрами показывает размер выбранного поднабора, не запускает решатели и не сужает сохранённый общий каталог.

## Что именно входит

Скрипт рекурсивно находит C++ программы с полным интерфейсом `instance.json → solution.json` и аргументом TL, Python программы с таким же интерфейсом, исходники посылок внутри ZIP. Учитывается текущий модульный `solver/` со всеми транзитивными локальными include, серверные и экспериментальные версии, промежуточные полноценные кандидаты, архивный Python-решатель. Версии пересобираются одинаково: `g++ -O3 -std=c++17 -pthread ... -ldl`; команды сборки и хеши бинарников сохраняются. Makefile из ZIP не исполняется.

Дополнительно включены настройки `env` из найденных JSON-спецификаций **полных прогонов**, если спецификация указывает доступный исходник. `DBG=1`, `NT=2`, TL и seed задаёт этот скрипт; прочие настройки различают конфигурации. Произвольные старые варианты, заданные только в shell/Python-коде и не сохранённые как отдельные исходники или JSON-конфигурации, автоматически восстановить нельзя. Бинарники без исходников не исполняются вслепую. Драйверы offline-oracle, постобработки checkpoint и unit-тестов не являются самостоятельными решателями и перечислены в `excluded.csv`. Сейчас один полный снимок `experiments/boundary_beam/integration/solver/solve.cpp` исключён: у него отсутствует `base.h`; полноценные упакованные boundary-версии включены. Ошибки сборки и отсутствующие зависимости записываются в `sources/<id>/build.json`, `build.log` и `blocked_variants.json`; они не считаются выполненными тестами.

Тесты — все существующие JSON в проекте с шестью полями официального instance, включая `task`, синтетику в `results/local` и экспериментальные наборы. Новые тесты не генерируются. Зависимости, Git, `to_delet` и каталоги этого бенчмарка исключаются из обхода. Все прежние holdout здесь — уже известные regression/development данные.

Одинаковые тесты объединяются по каноническому JSON; сохраняются все имена и хеши исходных файлов. Одинаковые исходники объединяются по тексту с раскрытыми локальными include; все имена сохраняются. Разные `env` остаются разными конфигурациями. Названия v4/v7, указывающие на один и тот же код, не расходуют TL повторно. Снимки входов защищены от записи и предоставляются отдельным запускам через hard links, чтобы не размножать большие матрицы расстояний на диске.

## Время, валидность и сохранение

Каждый запуск получает TL280 через argv и `TL`, `NT=2`, свой `SEED`. Независимый GNU timeout и дополнительный watchdog в Python останавливают зависший процесс при **TL+3 секунды**, затем допускает до секунды на прекращение. Время измеряется и сохраняется целиком. Ответ после внешней остановки отмечается `timeout`, даже если incumbent валиден; его балл сохраняется для диагностики. Ошибка процесса с валидным incumbent также остаётся `runtime_error`. Это позволяет различать качество incumbent и готовность полного решателя укладываться в бюджет.

Официальный валидатор копируется в исследование; его код не меняется. Проверяются все его ограничения, включая workers, баланс количества сайтов и попадание **всех** входных точек в оболочки с границами. Само пересечение полигонов не считается нарушением. Дополнительная геометрическая статистика считается после завершения решателя и не входит в его wall/CPU время.

Результат сохраняется отдельно после **каждой** завершённой пары «конфигурация × тест × seed». У результата и всех ответов/логов проверяются SHA256. Повреждённый/неполный кэш повторяется; Ctrl+C не помечает текущую задачу завершённой. Сохранённые invalid/runtime_error/timeout по умолчанию тоже пропускаются, чтобы не застрять на одной ошибке. Для их повторения:

```bash
.venv/bin/python -u tools/benchmark_all.py run --retry-failed
```

Каждый повтор получает новую папку `attempt-*`; предыдущие попытки сохраняются. Во время запуска решатель получает только свежий рабочий каталог с `instance.json`; предыдущие ответы, warm starts и исследовательский кэш ему не передаются.

## Какие файлы передать для анализа

Каталог по умолчанию: `results/local/all_solvers_tl280/`.

- `manifest.json`, `catalog_variants.csv`, `catalog_cases.csv`, `excluded.csv` — точный состав, происхождение, параметры, хеши и причины исключений.
- `summary.csv` — плоская таблица статусов, баллов, времени, RSS, CPU, компонент objective, числа офисов/сайтов/работников.
- `results.json` — индекс запусков с путями к подробным артефактам и хешами.
- `progress.json`, `events.jsonl` — прогресс и журнал завершённых запусков. Источник истины для восстановления — отдельные `runs/<job_id>/result.json`.
- `runs/<job_id>/attempt-*/work/solution.json` — полный ответ. Рядом — stderr/stdout, `resources.txt`, `started.json`, `analysis.json`.
- `analysis.json` — reward, distance, стоимость офисов, штраф нагрузки, sites/workers по офисам, task load и число сайтов, оболочки с координатами, площади/периметры, покрытые входные точки, допустимые пересечения оболочек без общей входной точки.
- Снимки ответов на 60,120,200,260 секунде и их анализ позволяют разбирать поздние изменения. Если ответ в этот момент ещё записывался, сохраняется ошибка захвата, без подмены более поздним результатом.
- `sources/`, `inputs/`, `validator.py`, `runner_snapshot.py`, `dependencies.json` — замороженные данные для воспроизводимости.

Для начала анализа достаточно `summary.csv`, `results.json`, `manifest.json`; для разбора геометрии нужны также ответы, `analysis.json` и входы. Лучше сохранить весь каталог. `tar` сохраняет hard links и не размножает одинаковые входы:

```bash
tar -czf all_solvers_tl280.tar.gz -C results/local all_solvers_tl280
```

Архивировать после остановки/завершения бенчмарка. Скрипт не меняет текущий решатель, старые отчёты, `results/best*`, Git или конкурсные посылки.

## Короткая проверка инфраструктуры

```bash
.venv/bin/python tools/test_benchmark_all.py -v
```

Это отдельные маленькие C++ заглушки, а не TL280-прогон реальных решений. Пять интеграционных тестов проверяют дедупликацию, заморозку, возобновление, блокировки, Ctrl+C, принудительное убийство Python и независимый watchdog, таймауты/ошибки, повтор повреждённого кэша, снимки, пустой вход и правило геометрии с допустимым пересечением полигонов.
