# Аудит модели и пространства поиска

Источник семантики: task/Techarena.pdf (локальная текстовая выписка
official_statement.txt) и task/validate_solution.py. Исходники v4/v8 проверены
по заданным SHA256; действующий solver/ не использован как baseline.

## Геометрия

Правило — disjoint множества **покрытых входных точек**, а не disjoint полигоны.
Входные точки = все сайты + все офисы независимо от их назначения/открытия.
Граница включена. Повтор координат не отменяет правило: все совпадающие входные
точки получают одинаковое покрытие. Для коллинеарных оболочек проверяется
отрезок; при совпадении всех координат — точка. Никакого положительного tol
у официального covers по умолчанию нет.

Минимальные свидетельства сохранены в inputs/, solutions/ и logs/oracle/:

| Случай | Официальный результат |
|---|---|
| cross_segments: два пересекающихся отрезка, 2 сайта/2 офиса | 18, VALID |
| cross_triangles: пересечение положительной площади, ни одной общей входной точки | 38, VALID |
| unassigned_witness / boundary_witness: неназначенный сайт в пересечении | Hull conflict |
| closed_office_witness: закрытый офис в пересечении | Hull conflict |
| disjoint_collinear | 18, VALID |
| overlap_collinear / coincident_boundary | Hull conflict |

Важный отрицательный вывод: **финальная геометрия v8 уже правильная**.
В frozen_v8.cpp строки 395–396, apply_cov/geo_ok (542–555), verify (801–872)
используют point footprints. Запрета пересечения рёбер в этих путях нет.
Геометрический state-test принимает cross_segments и сверяет 2000 случайных
изменений с независимой полной пересборкой cov/incov/count/load/need/sig.

Ограничения до проверки:

* Fast/power, сектора, гильотина строят безопасные подсемейства. Это ограничивает
  разнообразие стартов, но не является глобальным запретом всех пересечений:
  road-конструктор и Engine::doAdd способны построить пересекающиеся оболочки.
* move_resplit (1894+) и Exact2 (2970+) перебирают разделения прямой. Exact2 точен
  внутри этого семейства, не во всём допустимом пространстве двух офисов.
* move_resplit (1913–1918) включает свободный сайт только если первый по дороге
  открытый офис принадлежит выбранной паре. Хорошее назначение в другую пару
  может не попасть даже в пул.
* I.cand (355–363) содержит **все** офисы. Сокращение делается позже:
  recreate (2061+) topk; greedy_fill (2198+) первые 6; single LNS первые 5.
* geo_ok при последовательном добавлении корректен, если все снимаемые опоры
  уже удалены. Проверка на ещё не изменённой соседней оболочке блокирует
  пакетный перенос; исправление — атомарно снять весь выбранный пакет.
* Engine::doOpen отклоняет офис, покрытый текущей зоной. Это необходимо для
  данного состояния, но пакетное снятие опор до открытия даёт другие варианты.
* BoundarySearch (2360+) оставляет минимум один сайт в каждом текущем офисе;
  selector (2488+) не выбирает последний сайт. Costs постоянны, новые офисы
  не входят в ops. Это осознанная геометрическая окрестность, не структурная.
* Кеши покрытия: char incov по (офис, входная точка), int16 cov по точке.
  Все точки присутствуют в GeoGrid; индекс только broad phase, затем точный
  binary64 предикат. Протестированы совпадения/границы/отрезки/коллинеарность.

Новый B&B использует все домены выбранных офисов и тот же корректный point rule,
снимает все выбранные сайты прежде добавлений и перечисляет допустимые маски
офисов. Новый MILP использует независимо вычисленные Shapely footprints и cuts.
Ни один из них не запрещает пустые пересечения полигонов.

## Workers, counts и load

Один рабочий может обслуживать любое количество задач своего офиса, но не два
офиса. Требования навыков — множества; load — число задач **с повторами**.
Counts — число сайтов. Новая модель не подменяет одно другим.

Профиль pr = точное множество навыков рабочего. u[o,pr]∈{0,1},
Σ_o u[o,pr]≤число работников профиля; x[s,o]≤Σ_{pr содержит k}u[o,pr]
для каждого требуемого k. Не более одного идентичного профиля в офисе достаточно:
второй идентичный работник не даёт новых навыков и не увеличивает capacity задач.
Из u восстанавливаются конкретные индексы работников без повторов.

Независимый малый oracle сначала полностью перечисляет назначения конкретных
работников, затем назначения сайтов. Он не использует эту профильную MILP,
skill-count фильтр, домены кандидатов или разделяющие прямые. Дополнительно
11000 проверок покрытия используют Caratheodory + рациональные предикаты,
отличные от monotone-chain/GEOS. Численные probes также сохранены.

## Две точные условные MILP-окрестности

G: выбранные boundary/support сайты нескольких соседних зон; набор открытых
офисов фиксирован, остальные site assignments фиксированы, workers совместные.
S: выбранные целые маленькие зоны, соседние boundary/free сайты и закрытый офис;
маска офисов переменная, workers совместные. Остальные назначения фиксированы.

Цель: const_fixed + Σ pr[o,s]x[s,o] − Σcost[o]y[o] − alpha*(hi−lo).
Counts c[o]=fixed_count[o]+Σx, load L[o]=fixed_load[o]+Σntask[s]x.
c[o]≤maxSize[o]y[o], c[o]≥y[o], ch≥c[o], cl≤c[o]+N(1−y[o]),
ch−cl≤A; hi≥L[o], lo≤L[o]+T(1−y[o]), hi≥lo. T — сумма всех задач.
Поэтому внешние counts/loads/costs и глобальный penalty не теряются.

c≥y использует доминирование пустого открытого офиса при cost≥0,alpha≥0:
закрытие убирает cost, не расширяет диапазон counts/load и убирает hull.
Для отрицательных cost/alpha это неверно. Официальный Python schema не содержит
sign bounds; наша экономическая модель явно ограничена неотрицательным доменом.
Никакого заявления о полноте для произвольных signed JSON не делается.

Solve → все входные points → конфликт (a,b,q) → минимизировать supporting sets
назначенных сайтов, сохраняющих q в hull_a/hull_b → cut Σ literals≤|literals|−1.
В literals входят x supporting sites и y обоих офисов. Cut корректен по
монотонности convex hull, включая пересечение на границе и в вырождениях.
Нет общего polygon-intersection cut. Одни и те же матрицы/starts решают оба backend.

Время: build (включая начальную валидацию), solve, check/cuts, restore/официальная
валидация, wall; status, bound, gap, nodes и LP/matrix сохранены. На больших
checkpoint стоимость Python-валидации сама может исчерпать TL2; это отражено
как незавершённая модель, а не оптимальный ответ или конкурсное ускорение.

## Почему точность локальной модели недостаточна

Для нового офиса count должен быть ≥max_external_count−A. Если освобождено q
сайтов и этот минимум >q, открытие **невозможно внутри выбранной окрестности**.
Закрытие старого офиса тоже невозможно, пока хоть один его сайт фиксирован.
Это объясняет нулевую пользу структурного q12 на зрелых крупных зонах: увеличение
точности MILP/B&B не создаёт недостающие переменные.

Whole-zone packets меняют сразу большие части зон и маску офисов; кандидат
строится целиком, затем counts/load/geometry/workers/verify. Enumerated road и
coordinate templates не являются полной точной окрестностью; они умеют A=0
без q-сайтового барьера. Пример 63→114 подтверждён. Этот механизм не заменяет
доказательство выигрыша полного поиска и может проигрывать boundary при TL.

Все ухудшения остаются во внутренних попытках. Глобальный incumbent отдельный;
публикуется только при verify и положительном честном objective. Внутренние
надежды MILP/guide не публикуются. Все старые версии/чужие изменения сохранены.
