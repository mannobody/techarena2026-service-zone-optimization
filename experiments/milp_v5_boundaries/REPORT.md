## Что изменилось относительно v5

Новая стадия выбирает совместимые варианты выпуклых областей. В отличие от безопасного расширения v5, она позволяет переносить уже назначенные сайты между офисами. Исходные области и решение всегда входят в модель. Ответ публикуется только после полной native-проверки и только при улучшении текущего общего best.

Кандидаты: текущая оболочка каждого офиса; разделение объединённого пула пары офисов пятью линиями; обычные и взвешенные ячейки Вороного с предложением нового офиса. Проверяются три пары, ранжированные по потенциалу выигрыша от переноса сайтов с поправкой на расстояние, и один кандидат на открытие по оптимистической прибыли. Когда оболочка пары перекрывает третью зону по входной точке, строится безопасное подмножество жадным добавлением. Это эвристический генератор, не полный перебор всех геометрий.

Финальная исследуемая интеграция — один вызов в потоке 0 после 70% общего времени, максимум min(2 с, 3.5% TL). Он занимает один из существующих NT потоков; дополнительные рабочие потоки не создаются. Снимок назначения сайтов, офисов и работников снимается под одним mutex. Другие потоки продолжают поиск. При публикации заново сравнивается score с актуальным best. `own_gain` измеряется под mutex и относится именно к принятому региональному улучшению; обычное before/after во время параллельного поиска не позволяет такой атрибуции.

Все старые стадии, DP, генетический старт, boundary_finish и заключительный MILP v5 сохранены. SAFE_SOURCE_AUDIT.json подтверждает, что удаление нового заголовка, объявления и одного условного вызова с локальным флагом побайтово восстанавливает исходник предыдущего v5; это не заявление об идентичности машинного кода и многопоточной траектории. Default регионального оператора — фиксированные работники, поскольку совместная модель на многих входах слишком дорога. `REGION=0` отключает новую стадию; `MIP=0` отключает её и прежний MILP. `REGION_JOINT=1` — исследовательский совместный вариант; `REGION_MODE=1/2/0` — только пары / только ячейки / оба вида. Эти переключатели не являются рекомендацией для hidden-score без отдельного A/B.

## Модель и её точность

Для области e офиса o вводится бинарная z_e, для офиса y_o=Σ_(e∈o) z_e≤1. Для каждой входной точки p, включая необслуживаемые сайты и закрытые офисы, Σ_(e: p∈e) z_e≤1. Одинаковые строки покрытия объединяются. Пересечение областей без общей входной точки не запрещается: это соответствует правилам задачи.

Сайты внутри каждой области группируются по числу задач, а в совместном режиме также по множеству навыков. q_g — целое количество выбранных сайтов группы. Обозначим отсортированные прибыли p_0≥…≥p_(n−1), S_j=Σ_(i<j)p_i. Вместо отдельной бинарной переменной сайта используются непрерывная прибыль v_g и ограничения:

```
0 ≤ q_g ≤ min(n_g, maxSize_o) z_e
v_g ≤ p_j q_g + (S_j − j p_j) z_e       для всех различных склонов p_j
```

При z=1 нижняя огибающая этих прямых — прибыль q лучших сайтов, при z=0 q=0 и максимум v равен нулю. При дробном z это perspective-усиление исходной формулировки: оно соответствует распределённому выбору с 0≤x_s≤z и Σx=q. Ранний flow-прототип имел только 0≤x_s≤1 и Σx≤n z, поэтому его LP-релаксация могла быть слабее. Это усиление не гарантирует более быстрого MIP на каждом входе.

Общий принцип perspective reformulation для включаемых бинарным индикатором переменных разобран у Günlük–Linderoth: [Perspective Reformulation and Applications](https://optimization-online.org/2009/09/2393/). Формула выше — применение к нашей кусочно-линейной функции прибыли; она не требует нелинейного solver.

Ограничения ресурсов: n_o=Σ_g q_g, load_o=Σ_g tasks_g q_g, y_o≤n_o≤maxSize_o y_o. Общие переменные максимума/минимума количества заменяют квадратичный набор попарных ограничений: n_o≤C_hi, C_lo≤n_o+C(1−y_o), C_hi−C_lo≤A. Аналогично H/L задают размах нагрузки; цель — прибыль минус стоимости открытых офисов и alpha(H−L). C ограничен максимальной ёмкостью офисов, T — максимальной допустимой нагрузкой одной области. В совместном режиме профили одинаковых работников агрегированы, с ограничением их суммарного использования и покрытия навыков.

Из целого q восстанавливаются q лучших сайтов. Их оболочка с офисом лежит в выбранной выпуклой области, поэтому point-packing областей достаточен для допустимой геометрии. Модель консервативна: большая область может конфликтовать с другой, хотя оболочка фактически выбранного подмножества уже не конфликтует. Dual bound относится только к этому набору областей, а не ко всей задаче Service Zone Optimization.

## Что показали сравнения постановок

Пять тренировочных входов взяты из предыдущего независимого набора v5, solver seed 161. Теперь это development-набор. Для каждой модели ограничен весь дочерний процесс 60 секундами; сохранён проверенный checkpoint. Полные A/B ниже используют новые данные и общий TL=60.

Генерация областей ограничена wall-time. На больших входах она может прерываться в разных местах, поэтому размеры пулов между запусками иногда различаются. Таблицы показывают результат всего оператора; чистое сравнение скорости двух формулировок требует заранее фиксированного списка областей. На tiny-oracle списки областей одинаковы.

Проверены flow master, perspective master и perspective master с фиксированными работниками, каждый в режимах pair/power/both. Дорогая совместная модель может выигрывать при узком наборе областей, но не успевать после добавления новых вариантов. На alphabig0 power дал +1.4205%, а более широкий both в нескольких моделях за минуту не нашёл улучшения. Поэтому «учитывать больше» само по себе недостаточно.

Отдельная отрицательная проверка: четыре целых разбиения Вороного решались по очереди без выбора смеси областей. На всех пяти входах прироста не было. Выигрыш master связан с комбинацией старых областей и новых вариантов для отдельных офисов, а не просто с повторным запуском прежнего конструктора.

## Почему отброшено раннее размещение

Первый C++ вариант вызывал региональный MILP до запуска native workers. При TL=60 генетическая подготовка может занимать примерно 13.2 с, а отбор стартовых связок заканчивается на абсолютном PA=15 с. Двухсекундный MILP съедал оставшееся окно. В логе alphabig0/171 у кандидата осталась только fallback-запись `rank0 val=0`, у baseline — полноценный рейтинг стартов. Это конкретный механизм вмешательства в поиск; точную долю общего ухудшения, обусловленную каждым фактором, отдельно не измеряли.

Все 30 результатов этой проверки сохранены. В 6 из 15 кандидатных запусков в логе остался только нулевой fallback-рейтинг; у baseline таких случаев не было (logs/phase_a_audit.json). После неё выбран поздний вызов внутри одного рабочего потока; исходник зафиксирован до новой независимой серии. Ранний вариант не входит в финальный ZIP.

## Проверки и ограничения

Две Python-формулировки совпали с полным перебором на 30 tiny-инстансах каждая. C++ отдельно совпал на 30 совместных и 30 fixed-worker случаях. Это 120 сравнений четырёх реализаций на одном наборе из 30 tiny-инстансов, а не 120 независимых задач. В переборе присутствуют выбор областей, закрытие офисов, геометрические конфликты, баланс количества и нагрузки, отрицательные прибыли и многопрофильные работники. Оптимальность относится к конечному набору областей. В первом Python oracle допуск сравнения dual bound был слишком строгим: расхождение составило примерно 1e−6 при точном совпадении primal objective. Повторная версия допускает 1e−5 только для bound; допуск сравнения решений сохранён 1e−6. Первые логи сохранены.

В C++ покрытия областей вычисляются точными binary64-предикатами v4. Перед публикацией выполняется verify. Все сохранённые ответы дополнительно проверяет официальный валидатор. Python-прототип использует Shapely и служит исследовательской реализацией, не входит в посылку.

Для HiGHS используется тот же динамический C API, что и в v5, 32-битный HighsInt, локальная версия 1.15.1. Библиотека не включена в ZIP; при её отсутствии дополнительный поиск пропускается. Runtime читает только instance.json и пишет solution.json; модель передаётся в памяти. В ZIP нет Python, данных или локального LD_LIBRARY_PATH. Сборка g++ -O3 -std=c++17 -ldl, исходные оптимизации аллокаций v4 сохранены, стандартный лимит 280 с.

Измерения на общей машине, O3, NT=2, без CPU pinning; пары full A/B запускаются с одинаковыми параметрами. Параллельно выполнялись edge-проверки и часть диагностики. Три seed и положительное среднее не доказывают устойчивого преимущества на скрытых тестах. Внутренний time_limit HiGHS мягкий; фактический wall указан в таблицах. Ни код основного solver/, ни прошлые ZIP v4/v5 не заменены. Коммитов и отправки на сервер нет.


## Найденный дефект и его исправление

В coop_holdout60 один из 30 кандидатных процессов завершился SIGSEGV. При этом сохранённый JSON был валиден — это не превращает RE в успешный запуск. Анализ показал ошибочное предположение генератора: внутренняя маска isopen может содержать офис без назначенных сайтов. Базовый verify и serializer такие офисы игнорируют; новый генератор ранее добавлял офис в список, хотя add возвращал индекс −1 для пустого пула, и затем обращался к regions[−1].

Отдельный regression с пустым помеченным офисом воспроизвёл нарушение границ vector. С исправлением тот же тест проходит. Генератор и wrapper теперь строят локальную маску активности по реально назначенным сайтам; дополнительно проверяется индекс базовой области. Снимок общего решения не меняется. ASan-сборка была недоступна из-за отсутствия системной libasan; воспроизведение выполнено с _GLIBCXX_ASSERTIONS. Все диагностические логи сохранены.

Отброшенный ZIP помечен в artifacts/REJECTED.md. Исправленный исходник native_safe.cpp проверен повторно на исходном проблемном входе с тремя seed и затем на совершенно новом независимом наборе. Модель MILP и правило её вызова при исправлении не менялись. SAFE_SOURCE_AUDIT.json и logs/empty_office_regression.json содержат проверку изменений.

## Проверка архива и воспроизведение

26 edge/precision/crossing входов, TL60 NT2 SEED101: все валидны. Дополнительно два 60-секундных запуска без библиотеки/с MIP=0: валидны, обе MILP-стадии отключены. Архив распакован, пересобран через make build и отдельно запущен на 60 с, NT2, SEED155; wall 59.853 с, ответ валиден. На 10k-входе полный NT2 solver с TL60 имел peak RSS 47.961 МиБ, wall 59.825 с; это одно измерение, не верхняя оценка для NT16. Native source hash: `4144e63be49b938ca4885562dfd87bfdec78e46c8b3bd2ee9d32907997ff7bee`. Patch применён к исходнику старого v5 и побайтово воспроизвёл финальный source.

```sh
/tmp/ta-boundary-venv/bin/python experiments/milp_v5_boundaries/bench_full.py --tag repeat_new_tag --split safe_holdout --variants base,candidate --seeds 201,202,203 --seconds 60 --threads 2 --jobs 6 --exe native_safe
```

Скрипт `build_safe.py` без аргументов проверяет точное воспроизведение финального исходника из старого v5 и нового заголовка; `--output /tmp/v52-rebuilt.cpp` дополнительно создаёт и компилирует его. `BUILD_SAFE.json` хранит hashes этих компонентов.

Главные файлы: `src/region_mip_safe.h`, `artifacts/native_safe.cpp`, `regions.py`, `master_perspective.py`, `master_fixed.py`. Старый early-кандидат сохранён отдельно в `artifacts/native.cpp`. PATHS.json содержит полные пути ко всем данным и логам, MANIFEST.json — hashes. Ранние ошибки компиляции (локальная переменная pair закрыла std::pair), oracle-bound tolerance и неудачные постановки сохранены.

Следующий шаг определяется измерениями: дорабатывать генерацию совместимых областей и быстро проверять новые офисы с локальным перераспределением работников. Полная совместная модель при слишком широком наборе областей часто тратит минуту без улучшения; увеличение её бюджета без изменения постановки не обосновано текущими данными.
