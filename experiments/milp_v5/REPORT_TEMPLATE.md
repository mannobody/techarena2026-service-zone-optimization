# v5: практический MILP-хвост поверх v4

Исследование 19 октября 2026. Основной solver и архив v4 сохранены. Результаты относятся к синтетике и локальной машине; скрытые тесты сервера не запускались. Новый кандидат не содержит экспериментальную замену DP из dp_milp: базой служит именно frozen v4.

## Что реализовано

1. **Безопасное расширение территорий.** Начинаем с оболочек текущего лучшего решения. Пробуем добавить выгодные свободные сайты в оболочки, проверяя только геометрию, временно игнорируя ёмкости, баланс числа сайтов и работников. Каждое расширение обязано сохранить отсутствие общей покрытой входной точки с другими оболочками. Учитываются все сайты и офисы, включая необслуживаемые/закрытые. Пул MILP — обслуживаемые сайты внутри полученных оболочек. Для любого подмножества выбранных сайтов оболочка с собственным офисом остаётся внутри безопасного расширения. Поэтому геометрические cuts в MILP не нужны.
2. **Группировка сайтов.** В режиме фиксированных работников достаточно группы `(office, число задач)`; в совместном режиме — `(office, число задач, множество навыков)`. Внутри группы одинаковые ресурсы, поэтому выбор k сайтов эквивалентен k самым прибыльным. Дорожные прибыли сохраняются индивидуально, координаты после фиксации безопасного пула не влияют на этот выбор.
3. **Две точные линейные формулировки.** Первая использует целое k и непрерывную прибыль v с ограничениями по сегментам вогнутой prefix-функции. Вторая, выбранная для C++, использует целое k и непрерывные x_s∈[0,1], `Σx_s=k`, с исходной линейной прибылью. Для целого k оптимум этой группы достигается на top-k, поэтому при восстановлении можно безопасно заменить дробные x_s на целые выбранные сайты. Это сокращает число целочисленных переменных, но не устраняет сложность всей MILP.
4. **Ресурсы.** Совместно учитываются maxSize, maxDifference, целочисленная нагрузка и её размах, прибыль и стоимости офисов. Работники с одинаковым множеством навыков объединяются в профили. Binary u_(office,profile) сообщает, получил ли офис работника профиля; сумма по офисам ограничена числом таких работников. Два одинаковых работника в одном офисе не нужны: навыки не расходуются. Для каждой группы/навыка `k_group ≤ size_group * Σ u_covering_profile`.
5. **Два последовательных этапа.** Если после подготовки остаётся больше 0.65 с, MILP с фиксированными работниками получает до min(0.45 с, 40% оставшегося хвоста), затем модель с совместным распределением работников использует остаток. При меньшем остатке вызывается только модель с фиксированными работниками. Лучший результат первого этапа публикуется и передаётся дальше. Полная native-проверка с найденными MILP работниками выполняется до публикации; повторный эвристический поиск работников не может отбросить найденное назначение.
6. **Размещение финального кандидата.** Финальный native_v5 добавляет один вызов после boundary_finish, не меняя старые стадии или их временные бюджеты. Библиотека загружается только здесь, работники читаются из готового ответа в памяти. LAZY_SOURCE_AUDIT.json подтверждает байтовую идентичность старых модулей и main за исключением этого вызова. Это проверка исходников, а не идентичности машинного кода или расписания потоков. Deadline MILP — total_limit−0.15 с; внутренний лимит HiGHS мягкий, фактический wall указан ниже. `MIP=0` отключает оператор. `MIP_MODE=0/1/2/3` — фиксированная территория / расширение с фиксированными работниками / двухступенчатый режим / также предложения новых офисов. Default 2. `MIP_RESERVE` относится только к прежним прототипам и не действует в финальной версии.

В модели `n_o=Σ_g k_g`, `load_o=Σ_g tasks_g*k_g`. Цель `Σ_s profit_s*x_s−Σ_o cost_o*y_o−alpha*(H−L)`. Условия `y_o≤n_o≤maxSize_o*y_o`, `load_o≤H`, `L≤load_o+T*(1−y_o)`; разность количеств ограниченаA для открытых пар. Все нужные назначения u связаны с y. После целочисленного выбора k значения непрерывных x не используются как ответ: выбираются top-k исходных сайтов и полностью проверяется настоящая цель.

Старые непустые офисы финального кандидата сохраняются открытыми. Native default не переносит сайты между двумя существующими территориями и не открывает новые офисы. Это сознательно ограниченная окрестность, а не модель всей задачи. Геометрия контролируется при построении пула, все остальные перечисленные ограничения — внутри MILP. Условный dual bound не является глобальной верхней оценкой Service Zone Optimization.

## Что показали отдельные модели

Старый assigned-MILP уже доказал оптимальность многих финальных состояний v4; повторять его без расширения пула бессмысленно. Поэтому здесь проверены новые способы расширения и сокращения модели.

* Grouped hypograph:45 запусков (5 контролируемых +10 обычных входов × assigned/territory/joint), cap60 с, HiGHS1 поток, jobs4. На искусственных10k бинарный site-MILP заменился100 целочисленными количествами, но время всё равно исчерпывалось. Лучший assigned checkpoint435105.331196 против предыдущего binary HiGHS435086.264244; это малая прибавка без доказательства, не универсальное ускорение.
* Grouped continuous-profit flow:30 запусков (те же15 входов × territory/joint), cap60, фиксированные старые офисы. На10k варианты также исчерпали лимит; число integer variables само по себе не предсказывает скорость.
* Расширенные безопасные оболочки:20 запусков на10 обычных incumbents v4. Рост оболочек дал alphabig +1.91095%, tightA +0.59033%, large +0.19953%, latent0 +0.20413%; на части классов прироста нет. Добавление до3 новых непокрытых офисов не улучшило лучший grow-вариант; оно иногда ухудшало пул, занимая геометрическое пространство. В default не включено.
* Native post:10 incumbents ×3 режима, каждый с лимитом60. Фиксированные работники после расширения: alphabig +1.91095% примерно за0.041 с, large +0.19953% за0.073 с, huge +0.02797% за0.334 с. Совместные работники дали tightA +0.59033% за0.218 с, но на huge занимали почти60 с и не превосходили быстрый режим. Это основание для последовательности «быстрая модель, затем богатая», а не для безусловного большого MILP.

Это дополнительная постобработка уже полученного incumbent. Прирост к incumbent не следует выдавать за выигрыш полного solver при равном общем времени. Полные A/B приведены отдельно ниже.

## Механизм двух фактических улучшений

`logs/gain_mechanisms.json` содержит состав решений до/после, не только итоговый score.

* **alphabig0:**8 офисов, alpha155553.128459, A10. Старые нагрузки43/44 давали штраф155553.128459. После обменов сайтов все нагрузки стали43, штраф0; прибыль до стоимости офисов выросла10139203.141408→10161040.807678 (+21837.666269). Суммарный выигрыш177390.794728 (+1.91095%). Работники не менялись. MILP одновременно добавляет и удаляет сайты разных весов, чего не делает один DP по старому пулу.
* **tightA0:** A1; количества сайтов53/53/53/52 сохранены. Офис2 потерял необходимость в навыке3, офис6 получил этот навык; всего заменено30 сайтов. Прибыль выросла на882.750670, штраф за размах нагрузки увеличился на89.207757. Итог+793.542913 (+0.59033%). Это полезный совместный обмен: оптимум цели не обязан минимизировать размах нагрузки отдельно от прибыли.

## Проверки модели и геометрии

Python grouped-MILP:80 совпадений с полным перебором (40 tiny inputs × assigned/joint). Native C API selection:40 tiny fixed-open случаев и20 дополнительных случаев с многопрофильными работниками и конкуренцией за профили — совпадение с полным перебором сайтов и допустимых распределений работников. Условия включают A=0/1/large, alpha=0/.5/7/30, отрицательную прибыль и нулевые задачи. Точный oracle относится к соответствующему конечному пулу и выбранному режиму офисов.

Первый multiskill oracle ошибочно считал десятичные координаты `.1*j` строго коллинеарными после переноса наx=10/20: фактический hull не содержал весь заявленный пул. Провал сохранён, oracle исправлен на точно представимые binary64 `.125*j`;20 исправленных случаев прошли. Это дефект тестового предположения, не повод ослаблять геометрическую проверку. Также сохранены ранние ошибки runner (duplicate keyword, JSON numpy.int64, запуск ещё не собранного бинарника); они не учитываются как результаты solver.

Python результаты проходят официальный Shapely-валидатор. Native kernel использует точную binary64-геометрию v4 и дополнительный verify перед публикацией; каждый результат полных тестов проверяется официальным валидатором независимо.

## Библиотека и серверная сборка

HiGHS вызывается непосредственно из C++ через C API, Python не участвует. Runtime загружает `libhighs.so` или `libhighs.so.1`; проверяются необходимые символы и32-битный HighsInt ABI. При отсутствии библиотеки или несовместимости MILP отключается, продолжает работать native-база. Это не проверка фактического скрытого сервера. В ранее изученном предоставленном Dockerfile перечислен HiGHS1.15.1; локально проверена именно1.15.1. [Официальный C API](https://ergo-code.github.io/HiGHS/dev/interfaces/c_api/), [заголовок версии1.15.1](https://github.com/ERGO-Code/HiGHS/blob/v1.15.1/highs/interfaces/highs_c_api.h).

Архив содержит только main.cpp и Makefile: `g++ -O3 -std=c++17 -o solution main.cpp -ldl`, `make run` запускает `./solution`. Стандартный бюджет280 с. Модель передаётся в библиотеку в памяти; solver читает instance.json и пишет solution.json, без model-файлов, Python-процессов, внешнего warm start и сети. В исследовательских запусках путь к локальной библиотеке задавался LD_LIBRARY_PATH; в архив этот путь не зашит.

## Протокол и ограничения

GCC16.2.1, HiGHS1.15.1, PySCIPOpt6.3.0 используется только в research-зависимостях старого validator adapter. NT2 у полного solver, HiGHS1 поток в хвосте после join native workers. Постобработка NT1. Машина общая, без CPU pinning; полные тесты шли параллельно с edge-проверками и небольшими диагностическими задачами. Близкие различия шумные; три seed не доказывают устойчивости на скрытых тестах.

Python runner ограничивает дочерний процесс60 с и сохраняет проверенный checkpoint, до завершения процесса возвращает исходное решение при отсутствии улучшения. Очистка процесса может добавить десятки миллисекунд; фактический wall сохранён. Native тесты используют общий TL60; wall проверяется отдельно. Все исходники, старые логи и неудачные варианты сохранены; исходная реализация solver/ и архив v4 не перезаписаны, git staging/commit/push не выполнялись.

Полные абсолютные пути к коду, данным, скриптам, бинарникам и логам — в PATHS.json; hashes финальных артефактов — MANIFEST.json. Корень: `./experiments/milp_v5`.
