# v5: практический MILP-хвост поверх v4

Исследование 19 октября 2026. Основной solver и архив v4 сохранены. Результаты относятся к синтетике и локальной машине; скрытые тесты сервера не запускались. Новый кандидат не содержит экспериментальную замену DP из dp_milp: базой служит именно frozen v4.

## Что реализовано

1. **Безопасное расширение территорий.** Начинаем с оболочек текущего лучшего решения. Пробуем добавить выгодные свободные сайты в оболочки, проверяя только геометрию, временно игнорируя ёмкости, баланс числа сайтов и работников. Каждое расширение обязано сохранить отсутствие общей покрытой входной точки с другими оболочками. Учитываются все сайты и офисы, включая необслуживаемые/закрытые. Пул MILP — обслуживаемые сайты внутри полученных оболочек. Для любого подмножества выбранных сайтов оболочка с собственным офисом остаётся внутри безопасного расширения. Поэтому геометрические cuts в MILP не нужны.
2. **Группировка сайтов.** В режиме фиксированных работников достаточно группы `(office, число задач)`; в совместном режиме — `(office, число задач, множество навыков)`. Внутри группы одинаковые ресурсы, поэтому выбор k сайтов эквивалентен k самым прибыльным. Дорожные прибыли сохраняются индивидуально, координаты после фиксации безопасного пула не влияют на этот выбор.
3. **Две точные линейные формулировки.** Первая использует целое k и непрерывную прибыль v с ограничениями по сегментам вогнутой prefix-функции. Вторая, выбранная для C++, использует целое k и непрерывные x_s∈[0,1], `Σx_s=k`, с исходной линейной прибылью. Для целого k оптимум этой группы достигается на top-k, поэтому при восстановлении можно безопасно заменить дробные x_s на целые выбранные сайты. Это сокращает число целочисленных переменных, но не устраняет сложность всей MILP.
4. **Ресурсы.** Совместно учитываются maxSize, maxDifference, целочисленная нагрузка и её размах, прибыль и стоимости офисов. Работники с одинаковым множеством навыков объединяются в профили. Binary u_(office,profile) сообщает, получил ли офис работника профиля; сумма по офисам ограничена числом таких работников. Два одинаковых работника в одном офисе не нужны: навыки не расходуются. Для каждой группы/навыка `k_group ≤ size_group * Σ u_covering_profile`.
5. **Два последовательных этапа.** Если после подготовки остаётся больше 0.65 с, MILP с фиксированными работниками получает до min(0.45 с, 40% оставшегося хвоста), затем модель с совместным распределением работников использует остаток. При меньшем остатке вызывается только модель с фиксированными работниками. Лучший результат первого этапа публикуется и передаётся дальше. Полная native-проверка с найденными MILP работниками выполняется до публикации; повторный эвристический поиск работников не может отбросить найденное назначение.
6. **Размещение финального кандидата.** Финальный native_v5 добавляет один вызов после boundary_finish, не меняя старые стадии или их временные бюджеты. Библиотека загружается только здесь, работники читаются из готового ответа в памяти. LAZY_SOURCE_AUDIT.json подтверждает байтовую идентичность старых модулей и main за исключением этого вызова. Это проверка исходников, а не идентичности машинного кода или расписания потоков. Deadline MILP — total_limit−0.15 с; внутренний лимит HiGHS мягкий, фактический wall указан ниже. `MIP=0` отключает оператор. `MIP_MODE=0/1/2/3` — фиксированная территория / расширение с фиксированными работниками / двухступенчатый режим / также предложения новых офисов. Default 2. `MIP_RESERVE` относится только к прежним прототипам и не действует в финальной версии.

В модели `n_o=Σ_g k_g`, `load_o=Σ_g tasks_g*k_g`. Цель `Σ_s profit_s*x_s−Σ_o cost_o*y_o−alpha*(H−L)`. Условия `y_o≤n_o≤maxSize_o*y_o`, `load_o≤H`, `L≤load_o+T*(1−y_o)`; разность количеств ограниченаA для открытых пар. Все нужные назначения u связаны с y. После целочисленного выбора k значения непрерывных x не используются как ответ: выбираются top-k исходных сайтов и полностью проверяется настоящая цель.

Старые непустые офисы финального кандидата сохраняются открытыми. Native default не переносит сайты между двумя существующими территориями и не открывает новые офисы. Это сознательно ограниченная окрестность, а не модель всей задачи. Геометрия контролируется при построении пула, все остальные перечисленные ограничения — внутри MILP. Условный dual bound не является глобальной верхней оценкой Service Zone Optimization.

Совместные работники дали tightA +0.59033% за 0.218 с, но на huge занимали почти 60 с и не превосходили быстрый режим. Это основание для последовательности «быстрая модель, затем богатая», а не для безусловного большого MILP.

## Библиотека и серверная сборка

HiGHS вызывается непосредственно из C++ через C API, Python не участвует. Runtime загружает `libhighs.so` или `libhighs.so.1`; проверяются необходимые символы и 32-битный HighsInt ABI. При отсутствии библиотеки или несовместимости MILP отключается, продолжает работать native-база. Это не проверка фактического скрытого сервера. В ранее изученном предоставленном Dockerfile перечислен HiGHS1.15.1; локально проверена именно 1.15.1. [Официальный C API](https://ergo-code.github.io/HiGHS/dev/interfaces/c_api/), [заголовок версии 1.15.1](https://github.com/ERGO-Code/HiGHS/blob/v1.15.1/highs/interfaces/highs_c_api.h).

Архив содержит только main.cpp и Makefile: `g++ -O3 -std=c++17 -o solution main.cpp -ldl`, `make run` запускает `./solution`. Стандартный бюджет 280 с. Модель передаётся в библиотеку в памяти; solver читает instance.json и пишет solution.json, без model-файлов, Python-процессов, внешнего warm start и сети. В исследовательских запусках путь к локальной библиотеке задавался LD_LIBRARY_PATH; в архив этот путь не зашит.

## Связь с исследованиями и конкретная следующая модель

Использование MILP как ограниченного оператора улучшения соответствует направлению matheuristics: внешний поиск задаёт область, внутри которой работает MIP. В **Local branching** Fischetti–Lodi область ограничивается линейным условием на расстояние от incumbent; наша текущая геометрическая область задаётся безопасными оболочками, поэтому это не буквальная реализация Local branching. Источник: [статья авторов, 2003](https://www.researchgate.net/publication/225135001_Local_branching), DOI 10.1007/s10107-003-0395-5.

В RINS фиксируются целочисленные переменные, значения которых совпадают в incumbent и LP-релаксации; меньшую подзадачу решают MIP. Это могло бы ограничивать число изменяемых групп и назначений работников на больших входах, но в текущем ZIP RINS не реализован отдельно. Сначала следует измерить затраты на LP и долю зафиксированных групп: при хвосте менее секунды дополнительная релаксация может не окупиться. Источник: Timo Berthold, [Primal Heuristics in SCIP, раздел LNS](https://www.scipopt.org/download/slides/SCIP-primalHeuristics.pdf); [официальная реализация RINS](https://www.scipopt.org/doc-4.0.1/html/heur__rins_8c.php).

**Приоритет следующего эксперимента — MILP выбора вариантов оболочек.** Это предлагаемое расширение, не реализованный компонент посылки и не измеренный прирост.

Для офиса o заранее генерируем несколько выпуклых областей E_(o,e), каждая содержит сам офис: текущая оболочка, усечённые варианты у границы с соседом, расширения в освободившееся пространство. Для закрытого офиса добавляем кандидаты одновременно с усечениями соседних зон. В каждой области известны доступные сайты и множество покрытых входных точек — всех сайтов и всех офисов. Последнее вычисляем точной геометрией v4.

Вводим бинарные z_(o,e), выбирающие область, и y_o=Σ_e z_(o,e)≤1. Для каждой входной точки p:

```
Σ_(o,e): p∈E_(o,e) z_(o,e) ≤ 1.
```

Это ограничивает покрытие именно входных точек. Запрещать любое пересечение многоугольников было бы сильнее правил задачи и отбрасывало бы допустимые решения. Внутри выбранной области остаются групповые q_(o,e,g), непрерывные x_(o,e,s) и связь Σ_(s в группе g) x_(o,e,s)=q_(o,e,g), 0≤x≤z. Нагрузку и количество суммируем по вариантам области; работников распределяем между офисами, как в текущей модели. Условия навыков задаются для каждой группы. Стоимость офиса оплачивается один раз через y_o. Неактивные области имеют нулевые x и q.

Любой выбранный набор сайтов вместе с офисом лежит внутри выбранной выпуклой области. Поэтому point-packing выбранных областей достаточен для валидной геометрии результата. Однако он консервативен: две области могут конфликтовать по точке, которая после удаления сайтов уже не попадает в настоящие оболочки. Оптимум такой MILP — условный оптимум выбранных областей, не глобальный bound всей задачи. Добавление новых вариантов снимает часть этого ограничения.

Начинать стоит с пары соседних офисов и одного кандидата на открытие; остальные области оставить фиксированными. Но ограничения количества, нагрузки и распределение работников должны оставаться глобальными: локальный геометрический обмен может требовать компенсации в дальнем офисе. Текущие области и исходные назначения обязательно включаем как feasible warm start. Это позволяет принять только проверенный прирост.

Ожидаемый источник выигрыша: одновременное уменьшение двух старых оболочек может дать новому офису достаточно сайтов для глобального maxDifference. Простое расширение свободных зон этого не умеет; диагностика офиса 5 ниже показала этот конкретный барьер. Цена: несколько вариантов одного сайта увеличивают LP, а point-packing добавляет конфликтные строки. Для первого опыта ограничиваем число вариантов и удаляем дублирующиеся строки покрытия; не строим все пары сайтов.

Порядок проверки: brute force на tiny-пулах; одинаковые фиксированные incumbents с лимитом 60 с; отдельно измерить подготовку, LP bound, собственный gain и время до первого улучшения; лишь затем новый полный A/B с общим TL 60. В текущем исследовании положительный эффект доказан для расширения пула и совместных ресурсов, но не для этого нового мастера границ.

## Почему не включён split/reopen

Дополнительно проверены 6 диагностических случаев, до 60 с на пакет из до 9 локальных MILP: закрытый офис внутри старой оболочки получает половину этой территории, задаваемую разделителем между офисами; затем совместно выбираются сайты и работники. Везде сохранён исходный score. Часть узких моделей доказала оптимальность, часть исчерпала бюджет. В диагностике прежнего провала DP/large0 не предлагался пропущенный офис 5: он не входил в выбранные пары покрывающий офис→закрытый офис. Поэтому этот эксперимент не доказывает невозможность исправить тот провал — он показывает ограниченность данного генератора пула. Три фиксированных направления и top3 пары не исчерпывают геометрические перестройки. Bounds только для каждого пула. В default этот оператор не включён.

В split60 измеренный wall включает повторную проверку результата после выхода дочернего solver; у huge0 получилось 61.518 с, хотя дочерний процесс имел cutoff60. Это исследовательская диагностика, не часть native60 A/B и не заявленная серверная реализация split.

## Диагностика открытия пропущенного офиса 5

На прежнем DP-regression large0/seed111 входное решение 163270.803884 имело 8 офисов; известный native-baseline с 9 офисами —178722.967019. Закрытый офис 5 не покрыт старой зоной, поэтому split/reopen его не рассматривает. Обычное safe-grow с предложением нового офиса создало для него пул 64 сайтов; решение выросло лишь до 163335.211282, офис 5 остался закрытым.

Проверен отдельный new-first вариант: сначала расширять новый офис, до 2048 предложений для него и 5000 попыток всего, затем старые зоны. Пул офиса 5 вырос до 120 сайтов, но максимум текущих количеств 318 при A116 означает минимальные 202 сайта для нового офиса без сокращения остальных. Модель могла сокращать другие зоны, однако доказала условный оптимум 163334.222851 за 7.574 с вместе с построением. Большого выигрыша нет. Этот bound относится только к полученному пулу;120 — размер эвристически построенной оболочки, не верхняя оценка любой возможной зоны офиса 5.

Таким образом, больше времени на эту MILP не восстановит известное решение 178722.967019: его нет в пуле. Нужно совместно менять границы/освобождать пространство, либо предлагать несколько согласованных вариантов оболочек. Это отдельный диагностический вход, выбранный из известной регрессии; его нельзя выдавать за независимое подтверждение среднего прироста. New-first не включён в ZIP. Код и результаты: envelopes_newfirst.py, diagnose_newfirst.py, logs/reopen_newfirst60/; native diagnostic: logs/reopen_diagnostic60/.

## Проверки посылки, память и воспроизведение

Три packaged версии (с резервом 0.5, без резерва и финальная lazy) проверены на 26 edge/precision/crossing входах с конкурсными именами instance.json/solution.json, TL60 NT2 SEED101, jobs3. Все результаты валидны. Проверены отсутствие libhighs и MIP=0 (прототип native_v3, общий loader/disabled path): два 60-секундных запуска валидны; ещё два таких запуска выполнены на финальной lazy версии. Native MILP не требует файлов модели. На 10k-сайтовом incumbent staged post60 занял 59.68 с с пиковым RSS158.594 МиБ; это измерение одного NT1 post процесса, не верхняя оценка памяти полного 16-поточного solver.

Основная команда финального A/B (использовать новый tag, чтобы не переписывать сырые логи):

```sh
/tmp/ta-boundary-venv/bin/python experiments/milp_v5/bench_full_tail.py --tag repeat_lazy60 --split lazy_holdout --variants base,candidate --seeds 161,162,163 --seconds 60 --threads 2 --jobs 6 --exe native_v5
```

Финальный исходник `artifacts/native_v5.cpp`; это внутренняя пятая ревизия прототипа MILP, **не архив v4**. Посылка именуется v5_milp_lazy. Patch `artifacts/v4_to_v5_milp_lazy.patch` применяется к main.cpp распакованной v4 и даёт точно протестированный исходник. Для Makefile дополнительно нужен `-ldl`; новый ZIP уже содержит эту команду. Без внешней библиотеки runtime остаётся native; фактический hidden-host не проверялся.

Следующий предметный шаг для v5 — улучшать генерацию безопасных пулов: сдвиг общей границы пары зон, полезное открытие/закрытие офисов и перенос сайтов с пересчётом геометрии. Текущие результаты показывают, что быстрый count/load MILP уже умеет использовать свободные сайты; более дорогая постановка без подходящего пула часто не даёт ничего. Новый оператор сначала следует проверять на неизменном incumbent, затем — в полном равном 60-секундном бюджете с новыми seeds.
